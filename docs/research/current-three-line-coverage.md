# 基准客户场景三线能力现状核验

日期：2026-07-26

## 结论

现有仓库已经具备增长转化、轻量验真、渠道防窜三条产品线的大部分后台模块和数据模型，但尚不能称为一个可重复验收的产品闭环。

当前最准确的判断是：

- **增长转化：有活动、权益、领取记录和漏斗框架，但消费者入口不可运行，确认转化口径尚未闭合。**
- **轻量验真：解析 API 能返回码、产品和生产批次信息并记录扫码，但消费者页面不可运行，且同一码的页面配置与真实批次数据不一致。**
- **渠道防窜：渠道、流向、跨区线索和人工处置能力最接近闭环；处置 API 与数据库持久化已验证。**
- **基准数据不可重复创建：新租户能创建品牌、产品、SKU 和生产批次，但生成码批次被默认权限拦截。**

因此，下一阶段不应继续横向增加功能，而应先建立一套可重复初始化、可端到端运行、三条价值线口径一致的基准产品切片。

## 核验范围与方法

基准场景：

- 一个品牌
- 一个主力 SKU
- 一个生产批次
- 一批平台生成的一物一码
- 一个经销商及明确经营区域

验证方法：

- 本地 Docker 基础设施和真实 FastAPI 服务
- 真实 Admin 浏览器登录与页面检查
- 真实 H5 扫码页访问
- 真实 API 请求
- PostgreSQL 持久化查询
- 相关后端测试集

## 三条旅程覆盖

### 1. 增长转化

已有能力：

- Admin 可管理活动、权益、库存和领取数据。
- Demo 数据中有“首扫领券加企微复购活动”，并配置 20 元复购券和商城外链。
- 数据库共有 303 条权益领取记录，其中该活动有 41 条；Admin 与 API 展示一致。
- 已有扫码、领券、留资、加私域、GMV 的漏斗响应结构。
- 已有企微配置、外部联系人和 GMV 归因数据表。

未闭合点：

- H5 `/c/{publicId}` 因 `PointsHistory.tsx` JSX 语法错误返回 500，消费者无法完成扫码、领取和后续转化。
- Demo 的 5 个活动全部未关联产品，无法证明“某个主力 SKU 的扫码带来某个活动转化”。
- 最近 30 天漏斗全部为 0；现有领取数据不能直接证明当前扫码旅程。
- 数据库中 `wecom_external_contacts = 0`、`gmv_attributions = 0`，现有 demo 只有领取结果，没有确认加企微或确认成交。
- 企微相关测试出现预期 403/201、实际 401，确认转化路径当前测试不通过。

判断：**模块存在，端到端闭环未成立。**

### 2. 轻量验真与溯源

已有能力：

- 公开解析 API `/c/{publicId}` 返回码状态、产品、品牌、生产批次、产地和扫码信息。
- 两次真实解析请求均写入 `scan_events`，数据库可查询到最新扫码时间。
- 后台有产品、SKU、生产批次、码批次和页面配置模块。

关键缺口：

- H5 消费者页面编译失败，真实用户看不到解析结果。
- 码 `R56tJ3SRSN8` 的真实生产批次为 `DEMO-RICE-5KG-001-2026`，但其 `page_config.traceability.batch_code` 为 `DEMO-RICE-202605`，生产日期和到期日期也不一致。当前展示配置不是生产批次的单一事实来源。
- 同一批已有多次扫码记录的码，在本次新请求中仍返回并写入 `is_first_scan = true`。首扫语义需要明确并修正，否则会影响验真提示、首扫权益和风险判断。
- 普通二维码只能提供“平台记录与本次扫码信号”，不能单独证明实物绝对真伪；产品结果必须使用轻量验真措辞。

判断：**解析与记录能力存在，但消费者结果和数据一致性未达到可验收状态。**

### 3. 渠道防窜

已有能力：

- Admin 已有经销商、区域、门店、账号授权、流向登记和窜货线索。
- Demo 有 4 个经销商、9 个区域、14 个门店、1816 个已登记码。
- 跨区线索包含预期区域、实际城市、关联货品、渠道归属、风险等级、状态和人工处理建议。
- 通过真实 API 将一条线索标记为 `contacted_channel`，随后 API 和 PostgreSQL 均确认 `resolved = true`、处理记录和处理时间已持久化。

未闭合点：

- 风控中心请求不存在的 `/api/v1/risk-dashboard/alerts`，真实页面产生 404。
- 相关渠道测试中，门店创建被 403 拒绝，进而导致区域门店数、流向分配和账号范围测试失败。
- 本次浏览器验证已确认处理抽屉和必填处理结果存在；最终状态变更由 API 与数据库验证，尚未将浏览器提交动作纳入稳定验收。
- 跨区只能形成风险线索，不能自动判定窜货；必须保留人工核实、误报和调货等处置结果。

判断：**三条线中最接近闭环，但权限、接口契约和浏览器验收仍需收口。**

## 可重复基准数据阻塞

从一个新租户开始的自动化初始化实际执行到以下阶段：

1. 平台创建租户成功。
2. 新租户管理员登录成功。
3. 创建品牌、产品、SKU、生产批次成功。
4. 创建码批次失败：`403 Missing permission: code:generate`。

此外，当前 demo 重建命令会在导入阶段失败：

```text
ImportError: cannot import name 'BenefitType' from app.models.campaign
```

这意味着现有 demo 数据可以用于观察，但不能作为可靠的基准验收资产。后续验收矩阵必须把“从干净环境生成基准租户和三线数据”设为前置条件。

## 对后续规格的约束

后续三个决策票必须以本次事实为边界：

1. **增长转化口径**
   - 区分扫码、权益领取、留资、商城跳转、企微确认添加和确认成交。
   - 只有经企微回调验证并幂等处理的 `add_external_contact` 才计入确认添加。
   - 商城跳转是意向事件；GMV 只能来自导入或可信集成。

2. **轻量验真状态**
   - 产品/生产批次必须成为消费者展示的单一事实来源。
   - 明确首扫是“码的第一次有效扫码”，还是按消费者、设备或其他主体计算；不同语义不得共用同一字段。
   - 结果文案不能承诺绝对正品。

3. **防窜线索生命周期**
   - 线索由流向登记、预期区域、实际位置及信号质量共同形成。
   - 状态至少覆盖待核实、处理中、确认窜货、合理调货、误报和关闭。
   - 自动规则只生成/升级线索，不自动定罪。

## 建议的收口顺序

1. 修复 H5 编译和新租户默认权限，让基准场景可运行。
2. 修复 demo seed，使基准数据可重复重建。
3. 统一生产批次与消费者溯源展示的数据来源，并明确首扫语义。
4. 收敛增长确认事件和企微回调契约。
5. 将渠道人工处置纳入浏览器验收，并修复渠道测试与风控 404。
