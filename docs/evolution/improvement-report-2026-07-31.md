## 改进包列表

### 改进包 1: 试点客户上线门禁 [综合 RICE: 54.0]

**包含改进**:

1. **上线准备度单一事实源** [RICE: 45.0] — 把真实业务数据、人工交付确认和阻塞原因统一进一个可追溯状态，不允许浏览器勾选或 `onboarding_progress` 覆盖真实状态。
2. **客户级完整上线清单** [RICE: 27.0] — 将当前浏览器 localStorage 清单与代运营工作台的 4 项自动检查收敛为按租户持久化、可审计、可分配的清单。
3. **客户预览与上线确认** [RICE: 24.0] — 在内部页面预览之外，提供客户可访问的只读预览、反馈、确认/驳回、上线时间和确认记录。

**证据链**:

- `docs/01_product/PRD.md:142-151` 把代运营任务流定义为资料收集、配置、上线检查和复盘；`docs/03_delivery/GO_LIVE_CHECKLIST.md:8-82` 进一步要求租户、资料、码、H5、数据和客户确认。
- `frontend/apps/admin/src/app/(dashboard)/launch-checklist/page.tsx:94-127` 只把手工勾选保存到当前浏览器的 `localStorage`，没有租户、操作者、时间和审计维度。
- `backend/app/services/ops.py:37-56` 只检查品牌、产品、已发布页面和已激活批次，并将 `onboarding_progress` 与派生状态合并；`backend/app/services/ops.py:141-161` 仍以租户 JSON 作为初始化进度。
- `backend/app/models/tenant.py:179-200` 的 `OpsTask` 只有通用标题、描述、状态、优先级和截止日期，没有清单项、阻塞原因、客户确认或上线状态实体。
- 内部预览明确显示“草稿预览”，见 `frontend/apps/admin/src/app/page-preview/PagePreviewRenderer.tsx:137-142`；产品页面清单仍把“客户确认入口”列为独立协作入口，见 `docs/02_tech/PAGE_LIST.md:67-74`，当前没有对应客户确认路由/API。

**置信度**: High（PRD、交付手册、前端页面、后端服务、模型和页面清单六类证据一致）。

**建议 PRD 方向**:

围绕“一个客户何时可以上线”定义权威状态机：自动检查项、人工确认项、阻塞项、角色权限、客户确认凭证、重新打开规则和审计记录。代运营工作台应直接给出下一步动作，并能回答“为什么还不能上线、谁来处理、处理后如何继续”。

**下一步**:

→ `/prd-generator "为一码通实现试点客户上线门禁，包括统一准备度、客户级上线清单和客户预览确认"`

### 改进包 2: 试点数据学习与复盘 [综合 RICE: 43.2]

**包含改进**:

1. **试点里程碑与首个活动上线时长** [RICE: 36.0] — 记录客户开通、客户确认、正式上线、首扫和首个活动发布等时间点，形成可比较的上线效率指标。
2. **7/14/30 天复盘工作流** [RICE: 21.3] — 自动生成复盘任务，沉淀目标、数据结果、问题、动作负责人和下一次验证日期。

**证据链**:

- `docs/01_product/PRD.md:317-325` 明确定义“首个活动上线时长、客户活跃度、客户健康度”等运营指标，但当前租户模型没有这些里程碑字段。
- `docs/01_product/USER_JOURNEYS.md:48-64` 与 `docs/03_delivery/IMPLEMENTATION_PLAYBOOK.md:62-80` 都要求客户确认后上线，并在第 7/14/30 天复盘。
- 当前 `OpsTask` 只有通用任务字段，见 `backend/app/models/tenant.py:179-200`；API 也只提供通用任务 CRUD，见 `backend/app/api/v1/ops.py:97-211`，没有复盘对象、周期生成或 scorecard 结构。

**置信度**: High（PRD 指标、用户旅程、交付手册与当前模型/API 四类证据一致）。

**建议 PRD 方向**:

先定义最小试点 scorecard：上线效率、有效访问、权益确认、企微确认、订单/净 GMV、客户确认和复盘动作。每个指标写清分母、事件来源、归因窗口和数据状态；复盘必须能产生下一轮运营动作，而不只是静态报表。

**下一步**:

→ `/prd-generator "为一码通实现试点数据学习与复盘，包括里程碑、7/14/30 天复盘和运营 scorecard"`

### 改进包 3: 既有码接管与迁移交付 [综合 RICE: 18.0]

**包含改进**:

1. **既有码导入入口与结果追踪** [RICE: 18.0] — 把旧码导入、产品/批次导入、失败行、重复行和后续绑定收敛到可回查的客户流程；当前导入页请求不存在的记录接口并静默显示空列表。
2. **切换前验证与回滚** [RICE: 10.8] — 在正式切换前验证 DNS、证书、目标页和样本码，并保留回滚动作与切换记录。
3. **接管方案评估记录** [RICE: 9.0] — 对 CNAME、原系统中转、批量导入和重新贴码给出前置条件、限制、责任人和最终选择。
4. **客户域名/CNAME 接管配置增强** [RICE: 9.0] — 在现有域名 CRUD 基础上补齐真实 DNS 验证、SSL 状态来源、接管生效状态和变更历史。

**证据链**:

- `docs/01_product/PRD.md:83-92` 和 `docs/01_product/USER_JOURNEYS.md:109-120` 把域名接管、中转、旧码批量导入、灰度验证和新页面绑定定义为完整旅程。
- 后端已有 `POST /api/v1/imports/existing-codes`，见 `backend/app/api/v1/imports.py:193-270`，但没有对应的 `/codes/takeover` 管理页；当前 Admin 只有 `/imports`、`/codes` 等通用页面，未形成接管向导。
- `frontend/apps/admin/src/app/(dashboard)/imports/page.tsx:65-75` 请求 `/imports/records`，而 `backend/app/api/v1/imports.py:20-47` 及全文件路由中没有该端点；页面捕获错误后直接清空记录，导致用户看不到历史导入和失败明细。
- 自定义域名已有 Admin/API 表面，见 `frontend/apps/admin/src/app/(dashboard)/settings/branding/page.tsx:81-158` 与 `backend/app/api/v1/regional.py:488-550`；但 `backend/app/services/whitelabel.py:91-106` 明确是“简化版：标记为已验证”，没有实际 CNAME 检查。
- 当前未发现接管策略、灰度切换、回滚或评估记录的模型/API/页面，因此不能把基础域名配置当成完整接管能力。

**置信度**: High（PRD/用户旅程、前端入口、后端导入 API、域名服务实现和实际路由清单五类证据一致）。

**建议 PRD 方向**:

先定义首批客户可交付的 2–3 种接管策略及其前置条件，再建设一条可回查的接管向导：盘点旧码 → 选择方案 → 导入/绑定 → 样本码灰度验证 → 客户确认 → 切换 → 回滚。导入记录必须保存操作者、文件/批次、成功/跳过/失败数量和错误明细。

**下一步**:

→ `/prd-generator "为一码通实现既有码接管与迁移交付，包括导入结果追踪、DNS切换验证回滚和方案评估记录"`
