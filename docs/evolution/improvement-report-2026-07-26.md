## 改进包列表

### 改进包 1: 试点客户上线门禁 [综合 RICE: 54.0]

**包含改进**:

1. 上线准备度单一事实源 [RICE: 45.0] — 将真实业务数据作为权威状态，人工确认只覆盖无法自动判断的交付事项，避免 onboarding 标记覆盖实际状态。
2. 客户级完整上线清单 [RICE: 27.0] — 把当前浏览器 localStorage 清单与代运营工作台的 4 项自动检查收敛为可持久化、可审计、按租户隔离的清单。
3. 客户预览与上线确认 [RICE: 24.0] — 为客户提供只读预览、反馈、确认/驳回和确认记录，而不是只由运营人员在后台自行发布。

**证据链**:

- `docs/01_product/ROADMAP.md` 将 M3 定义为 1–3 个试点客户实际包装码上线并产生转化数据。
- `docs/03_delivery/GO_LIVE_CHECKLIST.md` 定义了租户、资料、码、H5、扫码、权益、数据和客户确认等完整门禁。
- `frontend/apps/admin/src/app/(dashboard)/launch-checklist/page.tsx` 仅把静态清单保存在当前浏览器 localStorage，无法形成客户级协作与审计记录。
- `backend/app/services/ops.py` 的工作台准备度只有品牌、产品、已发布页面和已激活码批次 4 项，并允许 `onboarding_progress` 覆盖自动派生状态。
- `docs/02_tech/PAGE_LIST.md` 明确列出“客户确认入口”，但当前前端路由和后端 API 未发现对应实质实现。
- 置信度: High（PRD/路线图、交付文档、前端页面、后端服务和路由五类证据一致）

**建议 PRD 方向**:

围绕“一个试点客户何时可以上线”建立权威状态机。PRD 应定义自动检查项、人工确认项、阻塞项、角色权限、客户确认凭证、重新打开规则和审计记录，并让代运营工作台直接给出下一步动作。

**下一步**:

→ `/prd-generator "为一码通实现试点客户上线门禁，包括统一准备度、客户级上线清单和客户预览确认"`

### 改进包 2: 试点数据学习与复盘 [综合 RICE: 43.2]

**包含改进**:

1. 试点里程碑与首个活动上线时长 [RICE: 36.0] — 记录客户开通、客户确认、正式上线、首扫和首个活动发布等时间点，兑现 PRD 的运营指标。
2. 7/14/30 天复盘工作流 [RICE: 21.3] — 自动生成复盘任务，沉淀目标、数据结果、问题、动作和下一次验证日期。
3. 真实转化结果归因 [RICE: 16.2] — 区分按钮点击、确认加企微、权益实际发放和订单归因，避免用弱代理指标代替业务结果。

**证据链**:

- `docs/01_product/PRD.md` 定义了首个活动上线时长、客户活跃度、扫码率、加私域率和 GMV 归因，但当前模型/API 未发现试点里程碑或首个活动上线时长记录。
- `docs/01_product/USER_JOURNEYS.md` 与 `docs/03_delivery/IMPLEMENTATION_PLAYBOOK.md` 都要求上线后 7/14/30 天复盘，当前工作台只有通用任务，没有复盘对象、报告结构或周期自动化。
- 企业微信已具备正式回调和确认联系人模型，但通用 `wecom_crm` 适配器仍保留未完成的回调验证路径；分析口径也需要明确区分点击与确认结果。
- 现有 `frontend/e2e/core-flow.spec.ts` 覆盖核心入口，但使用预置上下文分段验证，领取按钮不存在时也允许测试通过，不能替代真实试点结果验收。
- 置信度: High（PRD 指标、用户旅程、交付手册、模型/API 与 E2E 证据一致）

**建议 PRD 方向**:

先定义一个最小试点 scorecard：上线效率、扫码、转化、客户确认和复盘动作。所有指标必须写清分母、事件来源和时间窗口；复盘不是静态报表，而是能产生下一轮运营动作的工作流。

**下一步**:

→ `/prd-generator "为一码通实现试点数据学习与复盘，包括里程碑、7/14/30 天复盘和真实转化结果归因"`

### 改进包 3: 既有码接管产品化 [综合 RICE: 13.0]

**包含改进**:

1. 客户域名/CNAME 接管配置 [RICE: 8.0] — 将 PRD 中的域名接管从交付说明变为可配置、可验证的产品能力。
2. 切换前验证与回滚 [RICE: 10.8] — 在正式切换前验证解析、证书、目标页和样本码，并保留回滚方案。
3. 接管方案评估记录 [RICE: 9.0] — 对域名接管、中转、旧码导入和重新贴码给出可审计的选择与限制。

**证据链**:

- `docs/01_product/PRD.md` 将既有码接管列为 P0 场景，包含自有域名、CNAME、中转、批量导入和重新贴码迁移。
- `backend/app/api/v1/imports.py` 已实现既有码 CSV 导入，说明能力并非完全缺失。
- 当前模型、Admin 路由和 API 未发现客户域名/CNAME 生命周期、切换验证或回滚记录的实质实现。
- 置信度: High（PRD、已有导入实现与全仓库入口/API 交叉验证）

**建议 PRD 方向**:

不要一次建设完整域名平台。先围绕真实试点定义 2–3 种可交付接管策略、各自前置条件、验证清单和回滚动作；仅在首批客户确有旧码接管需求时进入实施。

**下一步**:

→ `/prd-generator "为一码通实现既有码接管产品化，包括域名接管、切换验证回滚和方案评估记录"`
