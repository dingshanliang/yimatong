# 基准数据与三线验收矩阵

状态：产品决策已确认  
确认日期：2026-07-26

## 1. 验收目标

本矩阵用于判断一码通标准产品是否完成，不代表真实客户试点或现场运营。

产品完成必须同时满足：

1. 基准数据可以从干净环境稳定重建；
2. 增长转化独立通过；
3. 溯源与轻量验真独立通过；
4. 渠道防窜独立通过；
5. 多租户隔离、角色权限及关键审计通过。

不采用总分或平均分。任何硬门禁失败或证据缺失，都阻止“标准产品完成”状态。

## 2. 基准数据结构

### 共享主数据

三条价值线共用一套权威主数据：

| 对象             | 最小数据                                 | 稳定业务标识示例                        |
| ---------------- | ---------------------------------------- | --------------------------------------- |
| 基准租户         | 1 个食品或农产品品牌方租户               | `TENANT-BASE`                           |
| 品牌             | 1 个                                     | `BRAND-BASE`                            |
| 产品与 SKU       | 1 个主力产品、1 个 SKU                   | `PRODUCT-BASE`、`SKU-BASE-001`          |
| 生产批次         | 1 个，含生产日期及溯源资料               | `PB-BASE-001`                           |
| 检测与资质资料   | 至少各 1 份有效资料                      | `REPORT-BASE-001`、`CERT-BASE-001`      |
| 码批次           | 1 个，由平台生成                         | `CB-BASE-001`                           |
| 经销商与授权区域 | 1 个经销商、1 个明确区域及有效期         | `DIST-BASE-001`、`REGION-BASE-A`        |
| 渠道流向         | 生产批次、码批次、经销商及区域的有效关系 | `FLOW-BASE-001`                         |
| 活动与权益       | 1 个活动、1 个可幂等领取的复购权益       | `CAMPAIGN-BASE-001`、`BENEFIT-BASE-001` |
| 页面             | 1 个已发布 H5 页面版本                   | `PAGE-BASE-001`                         |
| 外部数据源       | 企业微信连接器、标准订单导入源           | `WECOM-BASE-001`、`ORDER-SOURCE-BASE`   |

稳定业务标识用于定位场景和复现失败，不要求数据库内部 UUID 在每次重建后保持不变。

### 功能验收包

功能验收包使用约 20–50 枚码，按固定业务标识分配给以下受控变体：

- 增长：正常访问、重复访问、领取、留资、企微入口、企微确认、商城跳转、订单及退款；
- 验真：未激活、首次验证、正常重复、异常使用、冻结、作废；
- 防窜：区内观察、单次区外观察、持续偏离聚合、误报、正常调货、证据不足、确认窜货及重新打开；
- 负向控制：不存在的码、测试流量、未授权角色、重复请求和重复回调。

每个场景必须有明确的前置状态、操作步骤、权威预期结果和清理方式。随机数据不能作为硬门禁的唯一输入。

### 容量验证包

大量码和扫码事件由独立容量数据包生成，只用于性能与稳定性验证，不混入功能验收结果，也不能代替三线业务闭环。

## 3. 隔离对照租户

除基准租户外，建立一个最小隔离对照租户：

- 使用与基准租户相同或相似的品牌、SKU、码和用户名称；
- 只建立证明隔离所需的少量数据，不复制整套三线场景；
- 对基准租户的码、消费者、活动、权益、线索、报表、附件和导出执行跨租户负向访问；
- 平台支持流程如需跨租户访问，必须使用明确的绕过权限并产生审计记录。

对照租户不是第二个基准客户场景。

## 4. 干净环境重建门禁

预置 Demo 数据不能直接作为标准产品验收起点。每轮正式验收必须：

1. 从干净数据库或已清理的基准租户开始；
2. 通过受支持的初始化命令创建租户、默认角色和权限；
3. 成功创建共享主数据、功能验收包及隔离对照租户；
4. 验证默认角色具备其应有权限，包括生成码所需权限；
5. 执行全部三线旅程；
6. 连续重建两次，并确认业务结果一致、无重复脏数据。

初始化、种子脚本、默认权限或基准数据生成任一失败，三条价值线均不得开始验收。

## 5. 角色与权限

| 角色           | 正向能力                           | 必须验证的负向边界                   |
| -------------- | ---------------------------------- | ------------------------------------ |
| 品牌管理员     | 配置三线能力，执行授权的高风险操作 | 不得访问其他租户                     |
| 活动运营       | 配置活动和权益，查看增长漏斗       | 不得执行未授权的码处置或渠道定性     |
| 风控或渠道运营 | 调查异常和窜货线索                 | 不得越出租户或授权范围               |
| 经销商         | 查看自身相关线索并补充证据         | 不得裁定、关闭或查看其他经销商线索   |
| 代运营         | 操作明确授权的租户与能力           | 不得默认跨客户访问                   |
| 对照租户用户   | 操作自身少量数据                   | 不得访问基准租户任何业务数据         |
| 平台管理员     | 通过审计支持流程介入               | 不得以普通租户接口静默代替品牌方操作 |

冻结、解冻、作废、确认窜货和敏感数据导出必须验证原因、二次确认或明确授权，以及完整审计记录。

每项关键能力同时包含“授权角色成功”和“未授权角色被拒绝”的验收。

## 6. 证据标准

每个硬门禁场景必须形成三层验收证据链：

### 真实浏览器

- 从用户实际可达入口进入，不以直接拼接内部 URL 代替旅程；
- 完成真实点击、输入、确认和状态变化；
- 记录关键页面结果、可访问性和错误提示。

### 真实 API

- 记录关键请求的身份、租户、状态码和业务响应；
- 验证权限、状态机、幂等、错误边界和关键 payload；
- 仅返回 HTTP `200` 不能证明业务通过。

### 数据库持久化

- 查询权威业务状态、事件、归因、证据快照及审计记录；
- 验证租户隔离、关联关系和不可变历史；
- 页面表现与 API、数据库事实必须一致。

单元测试、组件测试和契约测试是补充证据，不能单独代替真实旅程。

## 7. 外部能力验收

### 自动化门禁

使用契约一致的可控服务覆盖：

- 企业微信验签、解密、重试、重复回调和失败回调；
- 浏览器定位授权、拒绝、不同精度及无位置；
- 标准订单导入、重复订单、取消和退款；
- 外部服务超时、失败和恢复。

### 发布前集成烟测

- 在非生产环境完成至少一次真实企业微信添加回调；
- 完成至少一次真实浏览器定位授权流程；
- 产品若声明支持具体订单连接器，则完成该连接器的真实回传；
- 产品若只提供标准文件导入，则以真实文件导入闭环验收。

自动化通过但真实集成烟测未完成时，只能标记“功能验证完成、外部集成待确认”，不能标记标准产品完全完成。

## 8. 增长转化门禁

| 场景         | 浏览器结果                     | API 与持久化结果                                        |
| ------------ | ------------------------------ | ------------------------------------------------------- |
| 有效访问     | H5 展示正确产品与生产批次      | 形成有效页面访问，进入增长分母                          |
| 访客去重     | 同一访客重复访问体验正常       | UV 去重，原始扫码次数独立保留                           |
| 权益领取     | 消费者成功领取权益             | 权益只发放一次，重复请求幂等                            |
| 留资         | 明确同意后成功提交             | 留资、授权版本和敏感数据正确保存                        |
| 企微意向     | 点击企微入口                   | 只记录意向，不生成确认转化                              |
| 企微确认     | 完成添加                       | 仅验签、解密且幂等处理的官方回调生成确认转化            |
| 商城跳转     | 成功进入外部商城               | 只记录意向，不生成确认订单                              |
| 订单与 GMV   | 导入后可查看订单结果           | 形成可信订单与净 GMV，取消和退款正确回冲                |
| 漏斗归因     | 后台展示访问人群漏斗与经营日报 | 分母、身份去重、7/30 天窗口、最后有效入口和数据来源正确 |
| 不可参与流量 | 显示对应状态或风险提示         | 无效、冻结、异常暂停及测试流量不进入增长漏斗            |

任一场景失败，增长转化线失败。

## 9. 溯源与轻量验真门禁

| 场景           | 消费者结果                                    | API 与持久化结果                           |
| -------------- | --------------------------------------------- | ------------------------------------------ |
| 首次验证       | 展示品牌、产品、SKU、生产批次、检测与资质资料 | 同一码只有第一条有效消费者验证被标记为首次 |
| 正常重复       | 展示首次验证时间和累计次数，不泄露他人信息    | 累计次数正确，不改写首次验证               |
| 异常使用       | 保留溯源，展示审慎提示并暂停权益              | 形成风险记录，不自动判假、冻结或作废       |
| 未激活         | 显示尚未启用，不展示完整溯源或权益            | 保持未激活并记录提前流出观察               |
| 冻结           | 显示核查提示并保留溯源                        | 权益暂停，授权人员可解除                   |
| 作废           | 显示失效，不提供正常验真或权益                | 状态不可恢复，保留作废审计                 |
| 查无此码       | 不泄露产品或租户信息                          | 记录受控的无效查询事实                     |
| 批次一致性     | H5 与后台展示相同生产批次                     | 页面、API 和数据库使用同一权威生产批次     |
| 验真与营销分离 | 首次参与按活动规则执行                        | 首次参与不会改变码的首次验证事实           |
| 处置权限       | 授权操作有清晰结果                            | 未授权角色被拒绝，原因与审计完整           |

任一场景失败，溯源与轻量验真线失败。

## 10. 渠道防窜门禁

| 场景               | 业务结果                               | API 与持久化结果                                     |
| ------------------ | -------------------------------------- | ---------------------------------------------------- |
| 区内扫码           | 不产生异常线索                         | 保存正常位置观察                                     |
| 单次低质量区外扫码 | 不自动生成正式线索                     | 只形成跨区观察并保存来源与精度                       |
| 持续偏离           | 形成一条待调查线索                     | 同一经销商、码批次、路径和窗口的观察正确聚合         |
| 证据快照           | 调查页面可看到创建时事实               | 流向、区域、定位、规则和阈值版本不可被后续主数据覆盖 |
| 经销商举证         | 经销商可提交调货、订单或物流材料       | 不得裁定、关闭或查看无关线索                         |
| 证据不足           | 只能选择继续观察                       | 无业务佐证时不能确认窜货                             |
| 确认窜货           | 授权人员补充佐证并记录理由             | 同时保留有效流向、可靠观察、业务佐证和完整审计       |
| 其他结论           | 可分别选择误报、正常调货或基础数据错误 | 处理进度与调查结论分开保存                           |
| 重新打开           | 新证据触发重新调查                     | 原结论和原证据保持不可变                             |
| 自动动作边界       | 系统只通知、聚合或建议                 | 不自动冻结码、停用渠道、扣罚或确认窜货               |

任一场景失败，渠道防窜线失败。

## 11. 隔离与共同门禁

以下失败会同时阻止三条线通过：

1. 基准数据无法从干净环境连续重建；
2. 默认角色权限不足以完成其正常职责；
3. 任意跨租户读取、修改、导出或对象存储访问成功；
4. H5、后台、API 与数据库中的权威产品或生产批次不一致；
5. 高风险业务动作缺少操作者、原因、时间或审计记录；
6. 关键场景缺少浏览器、API 或数据库任一层证据。

## 12. 验收结果契约

每个场景输出一条机器可读记录和对应的业务可读证据，至少包含：

- 场景名称与基准数据版本；
- `passed`、`failed` 或 `pending_external` 状态；
- 所属门禁及是否阻止发布；
- 租户、角色、码和稳定业务标识；
- 浏览器截图或录像；
- API 请求与响应摘要；
- 数据库断言及审计记录；
- 执行时间、代码版本和失败原因。

不允许使用“基本通过”。`failed` 和 `pending_external` 均阻止标准产品标记为完成。

最终汇总必须分别展示：

- 干净环境重建门禁；
- 增长转化门禁；
- 溯源与轻量验真门禁；
- 渠道防窜门禁；
- 多租户、权限及审计共同门禁。
