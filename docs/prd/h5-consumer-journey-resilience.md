## 1. Background

消费者 H5 有两条高频路径目前没有失败/进展闭环：

**现金红包发放状态**。领取端点（`POST /api/v1/benefit-claims`）对红包权益只做前置解析，实际发放由 worker 的 campaign claim outbox 异步执行，响应恒为 `status="pending"` + `claim_id`。前端领取卡停在"发放处理中"，无轮询、无终态：钱到没到、到多少、失败与否，消费者永远看不到。`/redpacket/result` 页面是无任何入口的孤儿页（全仓无跳转点），其"一般 1-3 分钟内到账"文案与真实链路不符——微信转账 pending 需等回调、重试退避最长可达小时级。发放事实分散在三处（`BenefitClaim`、`CampaignClaimOutbox`、`BenefitDelivery`），且不存在任何按 claim 查询状态的端点。

**扫码查验失败**。解析请求任意异常一次即渲染静态 `FallbackError` 卡片，无重试；`ErrorPage` 已支持 `onRetry` 渲染重试按钮但全站无调用方；重试按钮无 loading/防重复点击；客服电话硬编码占位、在线客服是死链。

现金红包在主 PRD 中定位为 P3 付费插件（不默认开通），但能力已在代码中完整落地并面向大客户开放；本 PRD 补的是消费者侧闭环，不改变主 PRD 的商务定位。

## 2. Problem

消费者领取现金红包或扫码遇到异常时，系统不能可靠回答：

1. 领取提交后，发放进展如何？到账了吗、到账多少？
2. 发放最终失败时，消费者如何得知？能自助重试还是需要找客服？预留的金额去哪了？
3. 弱网或瞬时故障下，扫码查验一次失败就是终态，消费者只能整页手动刷新。
4. 客服面对"红包没到账"的咨询时，没有一个消费者可读、口径一致的状态可引用。

如果继续放任：付费定制能力的不确定性直接转化为客诉与信任损失；扫码失败造成有效访问流失并污染漏斗上游数据；"处理中"承诺的 1-3 分钟与真实链路不符会放大投诉。

## 3. Goals

- 消费者领取红包后，在 H5 内看到发放真实进展直至终态：成功（含金额）、失败（含原因分类与补救入口）。
- 发放状态只有一个权威口径：由 claim → outbox → delivery 事实链派生，不新建并行业务流程或并行业务状态。
- 状态查询以 scan_token 绑定领取者身份：防枚举、防越权、独立限流。
- 扫码瞬时失败自动恢复一次；人工重试入口可用且可防重复点击；业务终态（已作废/未激活/风控）给清晰解释与客服路径，而不是无意义的重试按钮。
- 处理中文案不承诺与真实链路不符的到账时长。

## 4. Functional Requirements

### 4.1 查询权益发放状态（新增消费者端点）

- Actor: 消费者（H5）
- Trigger: 领取后查看发放进展（轮询或回访）
- Flow: 端点设计为权益类型无关（统一三态 + 类型相关字段），首版消费方为现金红包结果页，其他异步发放权益后续直接复用。GET 端点以 scan_token 鉴权；token 主体（consumer/tenant/码）与被查 claim 匹配才返回。状态由事实链派生为消费者三态 `processing / success / failed`：`success` 附实际发放金额与完成时间；`failed` 附原因分类（通道失败、风控暂停、收件信息缺失、系统异常），不暴露内部表结构与原始通道错误。
- Success: 同一 claim 在任何入口、任何时刻查询结果一致；状态单调推进（processing → 终态，终态不回退）。
- Failure: token 无效/过期、claim 与 token 主体不匹配、租户不匹配时返回统一的"不可查询"语义，不区分"不存在"与"无权"以防枚举；触发限流返回 429。

### 4.2 领取后状态闭环（专属结果页）

- Actor: 消费者
- Trigger: 领取动作返回 pending
- Flow: 领取受理成功后跳转到红包结果页（改造现有 `/redpacket/result`，当前为无入口的孤儿页），跳转携带仅对该笔领取有效的回访凭证；结果页轮询发放状态（短间隔起步、指数退避、总时长封顶），终态后展示成功金额或失败原因与补救动作。用户中途离开再回来（重扫该码或重新进入）时，若该笔领取仍非终态或已失败，提供"查看我的红包"入口回到结果页恢复状态，不要求重新领取。
- Success: 结果页不刷新即可推进到终态；处理中文案中性（如"通常几分钟内完成，长时间未到账可联系客服"）；回访用户能找回自己那笔的结果。
- Failure: 轮询到达时长上限仍在 processing 时，如实展示"仍在处理中 + 客服路径"，不伪装成成功或失败；回访凭证失效时展示客服路径，不静默空白。

### 4.3 发放失败的补救路径

- Actor: 消费者（自助）、客服/运营（兜底）
- Trigger: 发放进入失败终态（含 dead_letter）
- Flow: 失败终态必须伴随确定性补救：仅微信授权缺失/过期允许消费者自助（在结果页补授权后重试）；通道类失败由系统重试链兜底，消费者端只提供客服路径，不提供人工重发。预留金额在终态失败时必须释放或转入明确的人工处理队列。
  - 实现口径（评审确认）："在结果页补授权"以结果页上的**补救锚点**落地——锚点携带 `public_id` 回到该码页，重新完成微信 OAuth（OAuth 回跳契约本就落回 `/c/{public_id}`）后再次领取；上一笔失败终态已释放库存与预算，再次领取是新的一笔。不在结果页内直接拉起 OAuth（结果页无 scan_token 主体，静默换码权属于解析端点边界）。
- Success: 消费者始终有明确下一步；预留金额状态与消费者可见状态一致。
- Failure: 不允许出现"消费者看到失败但预算仍占用"或"消费者看到处理中而系统已终止重试"的分裂。

### 4.4 扫码失败重试

- Actor: 消费者
- Trigger: 解析请求异常（网络错误、5xx、超时）
- Flow: 瞬时异常自动重试一次（短暂退避）；仍失败展示"重新查验"按钮（接通 `ErrorPage.onRetry`，带 loading 态与防重复点击）。重试只针对瞬时故障；业务终态（已作废、未激活、风控拦截）不提供重试，按现有错误页语义给清晰解释。
- Success: 弱网场景一次自动重试即可恢复；人工重试可重复发起且不产生重复请求。
- Failure: 重试不得改变业务终态语义；连续失败时展示客服路径。

### 4.5 可配置的客服求助入口

- Actor: 品牌方（配置）、消费者（使用）
- Trigger: 失败页与"处理中/失败"状态展示求助入口
- Flow: 客服联系方式（电话/企微/链接）从品牌设置新增的租户字段读取；未配置时回退平台默认值。替换当前硬编码占位电话与死链。
- Success: 每个失败/等待状态都有可用、真实可达的求助入口。
- Failure: 不允许出现无配置时的空白或死链。

## 5. Roles and Permissions

- 消费者（scan_token 持有者）：仅可查询本 token 主体名下的 claim 状态；不可见其他领取者、内部重试细节、原始通道报错。
- 品牌方管理员：配置本租户客服联系方式；发放异常的运营兜底走既有 Admin 权限体系。
- 代运营人员：不参与消费者状态交互。
- 平台管理员：不参与消费者交互；仅通道级平台故障的受控处置。

消费者查询使用 RLS 消费者会话（`get_db_for_consumer`）或领取端点同款的 token → 租户上下文锁定模式；新增公开路由必须同步 `TenantScopeMiddleware` 白名单（注意该白名单按路径匹配、方法无关），并补认证边界与跨租户/越权测试。

## 6. Business Rules

### 6.1 消费者可见状态机

```text
processing → success | failed（终态，单调不可逆）
```

派生映射以事实链为准：claim/发放记录确认到账才可呈现 `success`（预留成功 ≠ 到账）；outbox/delivery 重试期间一律 `processing`；重试链终止（含 dead_letter）映射 `failed`。映射表在实现中显式定义并被测试锁定。

### 6.2 金额口径

`success` 展示的金额以实际发放金额（预留/结算金额口径）为准，分→元换算全局一致；`failed` 不展示金额。

### 6.3 时长承诺

处理中文案禁止固定到账时长承诺；文案上限须兼容 worker 真实退避链路（重试可达小时级）。

### 6.4 防枚举与幂等

状态查询不区分"不存在"与"无权"；轮询只读、不改变任何事实；领取幂等机制（幂等键 + request digest）不变，重复领取（replayed）返回既有 claim 的真实状态。

### 6.5 独立限流

状态查询使用独立 key 与配额（token 主体或 claim 维度），不复用领取的 IP 20 次/60s 桶，也不复用扫码的码维度 10 次/60s 桶（避免轮询几轮即封码）；Redis 故障时的语义（fail-closed 或放行+监控）必须显式选择并被测试覆盖。

## 7. Data and Integration Notes

- 不新建权威表：状态端点读取既有 `BenefitClaim` / `CampaignClaimOutbox` / `BenefitDelivery` 派生消费者三态；事实源唯一，前端不自行推断。
- scan_token 30 分钟时效：领取到终态可能跨时效，回访恢复凭证（复用领取响应中的 claim 引用或刷新机制）需在设计中明确（见 OQ-003）。
- 异步链路：发放重试与回调语义由既有 worker/outbox 承担；本 PRD 只保证如实展示，不改变发放权威路径（HTTP 请求内绝不调用外部支付的既有约束保持不变）。
- 测试基线：API 行为沿用 ASGITransport + 依赖覆盖模式；越权/枚举/限流用例进 `tests/test_isolation/` 与 API 测试；涉及 RLS、幂等契约补真实 PG 验收测试（acceptance 模式）。

## 8. Edge Cases

- scan_token 过期后回访：提供恢复路径，不把消费者锁死在"处理中"。
- worker 积压或长时间等待回调：页面如实"处理中 + 客服路径"，不伪造终态。
- 重试链终止（dead_letter）：消费者视角为 `failed` + 补救；预留金额释放或进入人工处理队列。
- 重复领取幂等命中（replayed/already_claimed）：展示既有 claim 的真实状态，不重复发起发放。
- Redis 不可用：限流故障语义与所选策略一致并有测试。
- 已作废/未激活/风控拦截的码：不出现重试按钮，展示解释与客服路径。
- 轮询期间断网：恢复后退避续查，不产生请求风暴。

## 9. Out of Scope

- 微信转账主动查单/对账通道（`WeChatPayTransferAdapter` reconcile）：另立需求跟踪。
- 现金红包风控规则与预算模型调整。
- 非现金权益（券、积分等）的前端展示接入：端点已通用化（OQ-004），其他权益接入为后续迭代。
- Admin 侧发放异常运营看板。
- 旧 `services/redpacket.py` 死代码清理（与消费者闭环无关，随技术债处理）。
