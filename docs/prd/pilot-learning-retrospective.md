## 1. Background

一码通的商业模式是"SaaS + 代运营交付"，客户成功依赖标准化交付动作：资料收集、配置、上线检查、上线后复盘。客户上线安全门禁（`yimatong-lls5`，2026-08 落地）已经回答了"什么时候可以上线"，但上线之后"跑得怎么样、下一步做什么"仍无系统承载。

当前系统已具备的数据基础：

- 上线时间线：`LaunchRelease` 持久化版本创建、品牌确认（`brand_confirmed_at`）、正式上线（`launched_at`）时间。
- 转化漏斗：有效访问/意图/权益/企微/订单/退款/净额七层漏斗与归因快照已落地。
- 客户健康度：`TenantHealthMetrics` 已有 `last_scan_at`、近 7/30 天扫码数和健康分。
- 任务提醒：`OpsTask` 通用任务（标题、负责人、截止日期、状态）。

缺失的是：把上述事实聚合成"每个客户上线后第 7/14/30 天该看什么、该做什么"的业务闭环。

## 2. Problem

客户正式上线后，系统不能可靠回答：

1. 这个客户从开通到上线用了多久？和别的客户比是快是慢？
2. 上线后第 7/14/30 天，谁应该看什么数据、得出什么结论、采取什么动作？
3. 上次复盘定的动作做了没有？下次什么时候验证？
4. 品牌方老板问"扫码活动效果怎么样"时，代运营拿什么一份可交付的、口径一致的回答？

如果继续依靠人工翻看板、口头对齐，代运营交付不可标准化，试点阶段最关键的"用数据学习、快速迭代"不会发生，客户健康度和续费也会受影响。

## 3. Goals

- 为每个租户建立可比较的试点里程碑时间线：开通、品牌确认、正式上线、首次扫码、首个活动发布。
- 上线后自动在第 7/14/30 天生成结构化复盘，包含目标、数据快照、问题、动作负责人和下次验证日期。
- 复盘数据快照来自系统真实事实（漏斗、归因、健康度），口径统一、可回查、可跨期对比。
- 复盘结果对品牌方可见，成为代运营向客户交付价值的固定触点。

## 4. Functional Requirements

### 4.1 记录试点里程碑

- Actor: 系统（自动），代运营/品牌方（查看）
- Trigger: 相关业务事件首次发生
- Flow: 系统从既有事件流派生并持久化每个租户的里程碑时间点：
  1. 客户开通（租户创建时间）
  2. 品牌确认（`LaunchRelease.brand_confirmed_at` 首次取值）
  3. 正式上线（`LaunchRelease.launched_at` 首次取值）
  4. 首次扫码（该租户首条有效扫码事件）
  5. 首个活动发布（该租户首个活动进入已发布状态）
- Success: 里程碑只增不改（同一里程碑首次记录后不被后续事件覆盖）；展示"开通→上线时长""上线→首扫时长"等派生指标。
- Failure: 某里程碑尚未发生时明确显示"未达成"，不允许人工伪造里程碑时间。

### 4.2 自动生成 7/14/30 天复盘

- Actor: 系统（生成），代运营人员（填写），品牌方（查看/补充）
- Trigger: 租户首次正式上线后第 7、14、30 天
- Flow: 到期自动生成该期复盘对象，预填本期数据快照；同时生成一条关联 `OpsTask` 提醒负责人完成复盘。
- Success: 复盘状态从"待填写"推进到"已完成"；完成后数据快照与人工结论一并归档。
- Failure: 逾期未填写的复盘标为"逾期"，不删除、不跳过；租户从未上线则不生成复盘。

### 4.3 复盘内容结构

每期复盘包含：

1. **期次与窗口**：第几天复盘、统计窗口（上线日至复盘日）。
2. **本期目标**：上一期复盘设定的验证目标（首期由代运营填写）。
3. **数据快照**：生成时点从系统事实计算的 scorecard（见 4.4），归档后不再随源数据变化。
4. **问题与判断**：人工填写，自由文本。
5. **动作清单**：若干动作项，每项含内容、负责人、期望完成日。
6. **下次验证日期**：默认下一期复盘日，可调整。

### 4.4 运营 scorecard

复盘快照与里程碑页共用同一套指标口径，每个指标明确分母、事件来源和归因窗口：

| 指标          | 口径                               | 事件来源        | 窗口                |
| ------------- | ---------------------------------- | --------------- | ------------------- |
| 开通→上线时长 | 首次 `launched_at` − 租户创建时间  | launch-releases | 全量                |
| 上线→首扫时长 | 首次有效扫码 − 首次 `launched_at`  | scan_events     | 全量                |
| 有效访问      | 有效访问层人数/次数                | 七层漏斗        | 本期窗口            |
| 权益确认      | 权益领取确认人数 / 有效访问人数    | 漏斗权益层      | 本期窗口            |
| 企微确认      | 企微添加确认人数 / 有效访问人数    | 漏斗企微层      | 本期窗口            |
| 订单 / 净 GMV | 归因订单数、净成交额（退款回冲后） | 归因快照        | 本期窗口 + 归因窗口 |

Success: 同一租户同一期复盘在任何入口看到的数字一致。
Failure: 某指标源数据缺失时显示"数据不足"，不得显示为 0 伪装成真实结果。

### 4.5 查看与对比

- Actor: 代运营人员（跨租户）、品牌方管理员（本租户）
- Flow: 代运营工作台展示各客户里程碑达成情况和待办复盘；品牌方后台展示本租户里程碑时间线与各期复盘结果。
- Success: 支持相邻期复盘对比（指标环比、上期动作完成率）。
- Failure: 品牌方仅可见本租户数据；代运营仅可见被授权租户。

## 5. Roles and Permissions

- 品牌方租户管理员/运营人员：查看本租户里程碑与复盘；可补充问题判断，不可修改数据快照。
- 代运营人员：对被授权租户生成提醒、填写复盘、管理动作项；不可修改里程碑与数据快照。
- 平台管理员：不参与客户复盘内容；仅通过受控留痕流程处理平台级技术问题。

所有查询和写入保持应用层租户过滤与 PostgreSQL RLS。

## 6. Business Rules

### 6.1 复盘状态机

```text
待填写 → 已完成
异常状态：逾期（超过下次验证日期仍未完成）
```

复盘完成后数据快照冻结；只允许追加补充说明，不允许改写历史快照。

### 6.2 里程碑不可变

里程碑是事实记录，只由系统事件首次发生写入；任何角色不能手工编辑或删除。纠错通过追加更正记录实现。

### 6.3 与既有事实源的关系

- 里程碑派生自 launch-releases、scan_events、campaign 状态，不新建并行业务流程。
- 复盘快照复用七层漏斗与归因快照的口径，不重新定义指标。
- `OpsTask` 仅作为复盘的提醒入口，复盘本体是独立结构化实体。

## 7. Data and Integration Notes

- 新增试点里程碑记录与复盘实体（含快照、问题、动作项），均含 `tenant_id` 并纳入 RLS。
- 复盘生成依赖定时任务（arq）按 `launched_at` 计算到期日，幂等生成（同租户同期不重复）。
- 快照在生成时点物化存储，后续源数据变化（如退款回冲）不改写已归档快照；当前看板仍展示实时口径。
- 与 `TenantHealthMetrics` 互补：健康分是实时监控，复盘是周期性人工+数据结合的学习动作。

## 8. Edge Cases

- 上线后暂停/回滚：复盘周期不重置，快照如实反映窗口内数据（含暂停期间低数据）。
- 租户从未正式上线：不生成复盘，里程碑页显示"未上线"。
- 复盘逾期后补填：标记"逾期完成"，保留逾期事实。
- 上期动作未完成：新一期复盘必须显式选择"继续/调整/放弃"，不允许静默消失。
- 数据不足（如窗口内零扫码）：快照显示"数据不足"，复盘仍可完成，问题判断中应说明原因。

## 9. Out of Scope

- 客户健康度评分算法调整（已有 `TenantHealthMetrics`）。
- 自动生成复盘结论的 AI 能力（后续可由 AI 辅助配置能力扩展）。
- 复盘报告导出/外发（PDF、邮件推送）。
- 跨客户基准对比看板（里程碑派生指标先行，横向基准后续迭代）。
- 外部订单退款/状态维护入口（改进包 2 跟踪）。
